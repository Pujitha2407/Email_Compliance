Email Compliance — Low-Level Design (LLD)

Project overview

This implements an email compliance analysis pipeline that ingests an email dataset, preprocesses messages, runs compliance analysis using an LLM (Azure OpenAI), computes a compliance score, and generates a JSON report. The orchestration entrypoint is [app.py](/Users/puji/Coding/Email_Compliance/app.py).

High-level flow

1. Read user configuration: categories and thresholds (user_config/categories.json).
2. Ingest email dataset from an Excel file (uploads/sample_email_compliance_dataset.xlsx) via EmailIngestionService.
3. Preprocess email bodies to normalize whitespace via PreprocessingService.
4. Run compliance analysis per-email using an LLM via ComplianceAnalysisService that builds prompts with compliance categories (compliance_prompt.py).
5. Compute a weighted compliance score and determine status via ComplainceScore and write report.json.

Components and responsibilities (detailed)

1) Orchestrator

- File: [app.py](/Users/puji/Coding/Email_Compliance/app.py)
- Responsibility: Wire up services, load user configuration, and run the processing pipeline.
- Key actions:
  - Loads user config from user_config/categories.json (expected JSON with a "categories" mapping and optional "threshold").
  - Initializes service objects:
    - EmailIngestionService()
    - PreprocessingService()
    - ComplianceAnalysisService()
    - ComplainceScore(user_config)
  - Executes the pipeline in sequence:
    - email_ingestion.execute("uploads/sample_email_compliance_dataset.xlsx")
    - preprocessing.execute(email_ingestion.get_emails())
    - compliance.execute(email_ingestion.get_emails(), risk_categories)
    - compliance_score.execute(email_ingestion.get_emails(), compliance.get_results())
- Inputs: user_config/categories.json, uploads/sample_email_compliance_dataset.xlsx
- Outputs: report.json (generated by ComplainceScore)

2) Email ingestion

- File: [services/email_ingestion.py](/Users/puji/Coding/Email_Compliance/services/email_ingestion.py)
- Responsibility: Read Excel dataset and transform each row into an internal email record.
- Expected input (Excel columns): Date, From, To, Subject, Body, Category, Classification, Column1
- Behavior and outputs:
  - Reads the Excel file using pandas.read_excel(file_path).
  - Strips whitespace from column names and normalizes Category and Classification cells (join split tokens).
  - Collects unique Category values into `self.risk_categories` and builds an `emails_db` dict keyed by incremental mail_id (int).
  - Each email entry structure produced is:
    {
      "email": {"from": <From>, "to": <To>, "subject": <Subject>, "body": <Body>},
      "metadata": {"date": <Date as string>},
      "risk": {"category": <Category>, "classification": <Classification>}
    }
  - Methods:
    - execute(file_path): fills self.emails_db and self.risk_categories
    - get_emails(): returns self.emails_db (dict)
    - get_risk_categories(): returns list of categories found in dataset
- Inputs: path to Excel file
- Outputs: Python dict mapping mail_id -> email record (see structure above)

3) Preprocessing

- File: [services/preprocessing.py](/Users/puji/Coding/Email_Compliance/services/preprocessing.py)
- Responsibility: Clean and normalize email content to reduce noise before analysis.
- Behavior:
  - iterate over emails dict items
  - normalizes whitespace in the email body using body = " ".join(body.split())
  - writes normalized value back to email["email"]["body"]
- Inputs: emails dict (from EmailIngestionService.get_emails())
- Outputs: in-place mutation of the emails dict

4) Compliance prompt builder

- File: [services/compliance_prompt.py](/Users/puji/Coding/Email_Compliance/services/compliance_prompt.py)
- Responsibility: Build a deterministic prompt string to send to the LLM for a single email analysis.
- Inputs:
  - email: Expected to be a dict containing keys: From, To, Subject, Body (see function signature)
  - risk_categories: list[str] of category names
- Output: a multiline string prompt instructing the model to return ONLY valid JSON with a precise schema describing whether a violation exists and supporting evidence.
- Expected LLM output JSON schema (exact JSON object only):
  {
    "violation": true|false,
    "categories": [
      {
        "category": "<Risk Category>",
        "reason": "<Why this category applies>",
        "evidence": ["<Exact quote from the email>", ...]
      }
    ]
  }

5) Compliance analysis (LLM invocation)

- File: [services/compliance_analysis.py](/Users/puji/Coding/Email_Compliance/services/compliance_analysis.py)
- Responsibility: For each email, build a prompt and call the Azure OpenAI Responses API to get a compliance judgment; parse the returned JSON and collect results.
- Key behavior:
  - Uses AzureOpenAI client instantiated with AZURE_OPENAI_API_KEY and AZURE_OPENAI_ENDPOINT environment variables and a configured model_deployment.
  - For each mail_id, builds a prompt via compliance_prompt.build_compliance_prompt(email, risk_categories)
  - Calls client.responses.create(model=model_deployment, input=prompt)
  - Attempts to parse response.output_text as JSON and saves it; on JSON decode errors, stores an error entry with raw_output for debugging.
- Inputs: emails dict, risk_categories list
- Outputs: results dict keyed by mail_id; values are either the JSON-parsed result or {"error": ..., "raw_output": ...}
- Notes on LLM usage:
  - Ensure AZURE environment vars are set and model_deployment is set to a valid deployment name.
  - The service expects the model to return strict JSON only (per compliance_prompt instructions). The code attempts json.loads(response.output_text).

6) Compliance scoring and reporting

- File: [services/compliance_score.py](/Users/puji/Coding/Email_Compliance/services/compliance_score.py)
- Responsibility: Compute per-email scores using user-configured category weights and generate a combined report JSON file (report.json).
- Inputs: user_config (constructor), emails dict (for context), emails_results (LLM outputs per mail_id)
- Expected user_config shape (user_config/categories.json):
  {
    "categories": {"CategoryA": <weight>, "CategoryB": <weight>, ...},
    "threshold": <numeric_threshold_optional>
  }
- Behavior:
  - calculate_score(emails_results): For each mail_id, sum weights for categories returned by the LLM and compute a combined score.
  - generate_report(emails, emails_results): create an object combining the original email, LLM result, and score, then write to report.json.
  - execute(emails, emails_results): runs calculate_score then generate_report.
- Output: `report.json` containing a mapping of mail_id -> {email, result, score}

Data contracts and formats (summary)

- Excel input: columns must include at least: Date, From, To, Subject, Body, Category, Classification.
- Ingested email record (internal):
  {
    "email": {"from": <str>, "to": <str>, "subject": <str>, "body": <str>},
    "metadata": {"date": <str>},
    "risk": {"category": <str>, "classification": <str>}
  }
- LLM prompt expects an `email` structure with top-level keys: From, To, Subject, Body (string). The LLM must return valid JSON matching the schema described in compliance_prompt.py.
- Score calculation expects user_config["categories"] to be a mapping of category names to numeric weights.

Error handling and logs

- ComplianceAnalysisService catches JSON decode errors from model output and records an error entry with raw_output for post-mortem analysis.
- EmailIngestionService assumes certain columns exist in the Excel file; missing columns will raise KeyError from pandas. Validate Excel column names before running.
- ComplainceScore defaults to threshold 50 if threshold is not present in user_config.

Known issues and recommended fixes (important)

While documenting the LLD, a few implementation issues were identified that should be addressed to make the pipeline robust and consistent:

1) Mismatch between ingested email structure and prompt builder expectations

- Observed:
  - [services/email_ingestion.py](/Users/puji/Coding/Email_Compliance/services/email_ingestion.py) stores each record under an `"email"` key with nested `"from"`, `"to"`, `"subject"`, and `"body"` keys (lowercase).
  - [services/compliance_prompt.py](/Users/puji/Coding/Email_Compliance/services/compliance_prompt.py) expects `email` param to have top-level keys `From`, `To`, `Subject`, `Body` (capitalized), and accesses them as `email['From']` etc.
- Consequence: A KeyError will occur in compliance_prompt when called with the ingestion output.
- Recommended fixes (pick one):
  - Update EmailIngestionService to produce a flat email dict with keys matching the prompt (From, To, Subject, Body), e.g. send a copy where these keys are top-level, or
  - Update compliance_analysis.py to pass `email['email']` (and ensure keys match capitalization), or
  - Modify compliance_prompt.build_compliance_prompt to accept the nested structure produced by ingestion (preferred for minimal changes: accept either a nested structure or normalize inside compliance_analysis before building a prompt).

2) Syntax bug and logic in ComplainceScore.calculate_score

- Observed:
  - Line using `score = high_risk + 0.2(score - high_risk)` is invalid Python syntax — multiplication missing operator.
  - The algorithm assumes self.risk_categories is a mapping category->weight; ensure user_config provides that mapping.
- Recommended fix:
  - Correct syntax to `score = high_risk + 0.2 * (score - high_risk)`
  - Validate types early: confirm that `self.risk_categories` is a dict; if ingestion provided categories as a list, they are not used by the scorer — this is OK because the scorer gets user_config mapping from app.py.

3) capitalisation and field naming consistency

- The codebase uses mixed conventions (some keys lowercased: `email['email']['body']`, some functions expect capitalized keys). Standardize on a single schema (suggestion: use lowercase keys, and update prompt builder to reference those) or normalize at the boundary between ingestion and analysis.

4) Dependencies and environment details

- The repository uses `pandas` and `azure-openai` (or a compatible OpenAI client). Add a `requirements.txt` listing pinned versions to make runtime reproducible. Example minimal contents:
  pandas>=1.5.0
  azure-openai>=1.0.0
